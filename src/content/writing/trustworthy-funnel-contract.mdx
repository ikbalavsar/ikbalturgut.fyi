A funnel can look deceptively simple: a few steps, a conversion rate, perhaps a drop-off chart.
But the chart is the last visible part of a longer agreement. Before it can be trusted, the
product needs to agree on what a step means, which population is eligible, how order is handled,
and which view settings change the answer without changing the funnel itself.

That agreement is the hidden contract behind the interface.

## A step is a definition, not a label

In a design file, a funnel step may be a short label such as “Viewed pricing” or “Started
checkout.” In a data system, that label needs a stable definition. It should point to an event or
condition, belong to the appropriate source, and be evaluated with explicit rules about order and
time.

Without those details, two people can look at the same step and assume different things. Does a
person need to perform the action after the previous step, or merely during the same date range?
Can they repeat a step? Is the funnel session-based, user-based, or event-based? Does the last
step have to happen within a conversion window?

None of these are implementation trivia. They are part of what the number means.

I find it helpful to treat the saved funnel definition as a small domain object rather than a
collection of form fields. It has a name, an ordered set of typed steps, a source-aware context,
and clear validation rules. That makes the product safer to extend because a new visualization
does not need to invent its own interpretation of the same funnel.

## Separate the saved definition from the current question

A saved funnel and the way someone is currently inspecting it are related, but they should not be
the same state.

The definition is durable: its steps, source, and business intent should survive a return visit.
The current question is temporary: a date range, attribution model, selected breakdown, page of
results, or search term. Persisting every temporary choice into the funnel definition makes a
shared object unexpectedly mutable. Keeping all of it only in local component state makes a view
hard to reload, share, or debug.

The URL is often the right home for the current question. It lets a page state say, in public and
inspectable terms, “show this funnel for this period with this breakdown.” A server request can
then be derived from the same state rather than from a separate, drifting copy inside the UI.

The distinction also clarifies product behavior. Changing a breakdown should request a different
view of the funnel, not silently rewrite the saved funnel. Editing a step should be a deliberate
save operation, not an accidental side effect of analysis.

## Let the API describe the shape it can support

Funnel interfaces often grow toward richer interactions: expandable rows, nested segments,
per-step comparisons, and sortable breakdowns. These are good ideas only when the response
contract can actually express them.

A flat, paginated breakdown table is a valid contract. A parent-and-child hierarchy requires more:
the API needs an explicit parent identity, child rows, aggregation rules, and pagination semantics
that do not separate related data. Rendering an accordion before that contract exists creates a
convincing visual promise that the data layer cannot keep.

This is why I start with response shape before polishing the interaction. Questions such as these
surface the real work early:

- Is the breakdown flat or hierarchical?
- What is the stable key for a row?
- Are totals computed before or after pagination?
- Which filters are applied before the result is grouped?
- Can every visible control be represented in the request?

The best answer is not always the most elaborate data structure. It is the smallest one that
accurately represents the product behavior people can use today.

## Make the request path boring enough to inspect

When a funnel looks wrong, the diagnosis should not require guessing which layer changed the
meaning. A predictable path makes that possible:

1. A control changes explicit view state.
2. The view state updates the URL or another durable representation.
3. The request is constructed from that representation.
4. The API validates tenant, source, and funnel ownership.
5. The response states the scope and shape that were applied.

This may feel more deliberate than wiring a chart directly to component state. It pays for itself
the first time a teammate shares a URL, compares an API response with the page, or asks why a
breakdown has changed a total.

## Trust is an explainability feature

A trustworthy funnel does not need to expose every internal detail, but it should be able to
answer basic questions without ambiguity: who is counted, which events qualify, in what order,
and under which current filters?

The chart earns trust when those answers are consistent across the UI, the URL, the API, and the
data model. Once that contract is clear, the visual layer becomes much easier to improve. Until
then, a beautiful funnel is only a well-presented assumption.
