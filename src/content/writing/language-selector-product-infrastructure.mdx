A language selector is often introduced as a compact navigation control: a label, two options,
and a preference that should persist. It is easy to treat it as a local component because that is
where people see it.

The component is the visible edge of a much larger system.

Once a product supports more than one language, language touches routing, content availability,
notifications, search, account preferences, legal copy, analytics, and support expectations. The
selector is simply the moment when a person asks the product to make a consistent decision across
all of them.

## There is more than one kind of language

The first useful distinction is between interface language, content language, and communication
language.

Interface language determines navigation, buttons, errors, and system feedback. Content language
determines which article, report, or help page a person receives. Communication language affects
emails, alerts, exports, and messages that may arrive long after the person last used the product.

These settings may have the same default, but they are not automatically the same preference. A
person might use an English interface while reading a locally authored report in another language.
Treating one preference as an unexamined answer to every language question makes future product
work unnecessarily painful.

## Separate what the product supports from what it displays

Teams sometimes need to simplify a selector temporarily: show one language while content or
translation coverage catches up. The dangerous shortcut is deleting other locales from the global
configuration because they should not appear in one place.

Support and presentation are different concerns.

A product-level locale registry can define every language the system understands: parsing rules,
formatting, translation resources, routes, and fallback behavior. A selector can define a smaller
list of choices appropriate for a specific surface. That keeps a temporary presentation decision
from breaking a stored user preference, a legacy URL, or a page that still legitimately uses a
supported locale.

This separation also makes the code more honest. A variable named `selectableLocales` tells a
reader that it controls the interface. A global `supportedLocales` registry tells them it is a
contract with consequences elsewhere.

## Decide where a preference lives

Language state needs a clear home and a clear precedence rule. Common candidates include:

- a locale in the URL, useful for shareable and indexable content;
- an account preference, useful for a signed-in person’s long-term choice;
- a cookie or local preference, useful for a lightweight anonymous experience;
- the browser’s `Accept-Language` header, useful as a first-visit default.

The important part is not choosing one universal mechanism. It is deciding which mechanism owns
which situation. A URL should generally win when someone opens a localized link. An account
preference may win after sign-in. A browser header should be a default, not a force that overrides
an intentional choice every time a page loads.

Writing that order down prevents a common class of bugs: a person selects a language, refreshes,
and sees the interface revert because a second layer made a different decision.

## Fallback copy is part of the experience

No translation system is complete forever. New product strings, CMS content, and transactional
messages all create moments where the requested language is unavailable. A fallback is not merely
a defensive engineering behavior; it is a customer-facing sentence.

Good fallbacks are predictable. They preserve the selected locale where possible, use a documented
default when necessary, and avoid mixing languages inside one critical action. If a report cannot
be shown in the requested language, the product should be able to say so clearly rather than
quietly switching the person into a different context.

## Small controls deserve system-level tests

The interaction itself still matters. On small screens, a selector should work without assuming
JavaScript has already enhanced the page. Keyboard and screen-reader behavior should expose the
same choices as pointer interaction. The visible label should reflect the active locale, not only
the default loaded by the server.

But the most valuable tests sit one layer deeper: does an existing localized URL still resolve?
Does a saved preference survive a new release? Does temporarily hiding a locale from a menu leave
other translated surfaces intact? Do fallback rules behave consistently in the app and in emails?

Thinking through those questions changes the selector from a fragile widget into dependable product
infrastructure. The control may be tiny. The promise it makes is not.
