An analytics filter often arrives as a small product request: add a dropdown, remember the last
choice, make the table easier to segment. But a filter is not only an interaction. It decides
which facts a person is allowed to see, which facts they expect to see, and how confidently they
can act on them.

That makes filtering a boundary-design problem.

In a multi-tenant product, a tenant, a source, a date range, a report type, and a consent mode
are not interchangeable pieces of UI state. Each one constrains the next. Treating them as an
unstructured bag of query parameters is how an otherwise clean interface starts returning
surprising data.

## Start with the question the filter is allowed to answer

The useful question is not “what fields should this page expose?” It is “what question can this
person safely ask of this dataset?”

For example, an event filter might let someone ask, “Which events occurred for this source during
this period?” The source is not a cosmetic refinement. It is the boundary that gives the event
name meaning. An event called `purchase` can be a useful fact in one source and an unrelated
string in another.

I try to make the constraints explicit before designing controls:

- **Tenant** determines the universe of data and identities.
- **Source** narrows that universe to an implementation context.
- **Report scope** decides which records are eligible to be counted.
- **Date range** decides when the question applies.
- **Breakdowns and search** refine a result only after the earlier boundaries are fixed.

This order matters. A search box that queries every event name before a source is selected feels
responsive, but it is asking an invalid question. The correct empty state is not “no results”; it
is “select a source to see its events.”

## Keep one source of truth for the scope

The easiest failure mode is letting each layer reconstruct scope for itself. The interface has
selected source A, the URL still has source B, and the API falls back to the tenant default. Every
individual decision is plausible. Together, they produce a page nobody can explain.

A reliable filter flow has one serialized scope that moves through every layer:

1. The user changes a control.
2. The page updates the URL or another durable state.
3. The request is built from that state, not from a second local copy.
4. The server validates every boundary again.
5. The response identifies the scope it was computed from.

The server-side check is not redundant. Client state is a request for data, not permission to
receive it. A tenant identifier, source key, or report scope supplied by the browser should be
validated against the authenticated context before it reaches a query.

## Make invalid combinations impossible to choose

Good filter design removes choices before it explains why they are wrong. If an event belongs only
to one source, do not show it under another. If a breakdown is unavailable for the selected report
scope, disable it with a short reason rather than returning a suspiciously empty table.

That principle is especially important when filters depend on one another. Resetting a stale child
selection may feel slightly disruptive, but retaining it is worse: it leaves the user looking at a
combination the system can no longer justify.

The interface should distinguish at least three states:

- No data exists for this valid scope.
- Data may exist, but a required parent filter has not been selected.
- The selected combination is not supported.

Those states deserve different copy, different actions, and often different visual treatment.
Lumping all three into “No results” turns a product constraint into a trust problem.

## The URL is part of the product contract

Durable analytics views should be shareable and reloadable. That usually means the active scope
lives in the URL. The benefit is bigger than link sharing: it makes the current question visible.
A teammate can inspect a URL and see the time range, source, model, and breakdown rather than
guessing what a screenshot represents.

This also creates a useful engineering constraint. If a filter cannot be represented clearly in
the URL, it is worth asking whether its state model is too implicit. The same discipline helps
with funnels, where a saved definition and a temporary analysis view should not be confused.

## Trust comes from narrow, explainable answers

Analytics products do not earn trust by exposing every possible slice of data. They earn it when a
person can understand why a number is present, what it includes, and what changing a control will
do to it.

The practical test is simple: when someone asks “where did this number come from?”, the answer
should be visible in the page state and enforceable in the request path. If it is only implied by
the UI, the boundary is not designed yet.
